# 看板主界面：打开看板就是打开协调者对话

Status: implemented
Translation: current

[English](2026-10-16-board-home.md)

## 摘要

第一版看板界面是一个独立的管理页，用户不会把它当成干活的地方。现在打开看板和打开对话一样：
侧边栏把看板和对话并列，打开后是协调者对话，旁边是放线程和文件的看板侧面板；不常用的设置
收进浮窗。面板复用会话侧面板机制，线程在面板里打开，但不变成 Side Chat。线程行只用元数据
和 presence，所以失败的线程在打开后、以及协调者收到的回报里才看得到，列表里不显示。

## 决定与依据

[设计文档](../../../../specs/project-coordinator/design.zh.md)的「看板主界面」一节记录了
用户 2026-10-16 的决定。本文对应第 1、2 步。

- **协调者就是看板。** 协调者的会话页增加 `board` 侧面板类型。单独做一个看板页，就得
  另做对话、输入框、面板布局和移动端抽屉，而会话页这四样都有了。`/boards/<id>` 保留为
  别名，带 `?board=1` 跳转。渲染阶段的恢复照搬 `?pr`：每个会话一个状态守卫，用完从 URL
  去掉，所以从侧边栏再次打开看板时还会生效。
- **线程不用 Side Chat 的 id。** Side Chat 的关闭路径会终止并删除会话，渲染路径也只接受
  本页的侧面板子会话。所以看板面板直接渲染 `SessionChatInterface`，把线程本身作为它的
  工作区会话（否则会显示协调者的仓库、PR 和 diff 状态），并且不传本页的文件和 diff 处理
  函数，因为它们绑定在协调者上。打开的是哪个线程存在页面状态里，因为紧凑布局会重挂面板。
- **在各列表的数据源处过滤。** `sessionListAtom` 和 `useVisibleSessionMetas` 还供命令面板、
  完成通知、PR 监视、提及和 Dock 计数使用，它们仍要看到协调者。侧边栏、移动端首页和归档页
  各自过滤。由被隐藏的协调者打开的会话，通过已有的 opened-by 树退回为顶层行。
- **侧边栏标记不加订阅。** `LoroAppSidebar` 已经维护一份引用稳定的实时状态映射；
  `boardActivity` 读它，等待判断和 `deriveBoardSessionStatus` 一致。
- **行不读文档。** PR1 只在展开的行上打开成员文档。面板没有展开；为了找失败而打开每个成员
  的文档，会破坏按需读文档的边界。状态来自 `sessionLiveStatusAtomFamily` 上的一个派生 atom
  加元数据。
- **归档与恢复。** 会话归档本来就包含协调者打开的会话；恢复只包括直接的子 Tab。所以归档
  依次处理协调者和每个成员根会话，再标记看板行；恢复时像创建一样在 catalog writer 里重新
  检查 50 个上限，逐个恢复根会话，最后才清掉标记。第一版先清标记，某个成员恢复失败时，
  看板已经离开归档页，再也没有恢复入口。现在看板行两个方向都最后改：失败时看板留在原处，
  入口（归档页或设置）还在，可以重试，提示里写明原因。不做事务或回滚，重试会跳过已经
  成功的部分。两个恢复同时读到 49 个未归档看板的情况，设计里已经接受：上限检查本来就不是
  分布式事务。
- **同一个会话只有一个界面。** 子 Tab 会继承看板，所以协调者自己的子 Tab 和 Side Chat 也是
  线程，而会话页已经挂着它们。之前在面板里打开会再建一个 `SessionChatInterface`，输入框
  草稿各存一份。现在协调者的直接子会话在会话页里打开：子 Tab 切换主区的 Tab，Side Chat
  切到它的侧面板 tab。聚焦输入框、查找这类命令按用户所在的区域选目标：焦点在可见的看板
  面板里时，作用于面板中打开的线程。
- **面板绑定看板。** 会话页在会话之间不重挂，所以在 A 打开的面板会把 tab 和设置草稿带到 B，
  保存时把 A 的草稿写进 B，还把 B 的协调者改了名。现在 `BoardSidePanel` 按工作区和看板 id
  给内容设 key，设置浮窗也按看板 id 设 key。
- **入口。** 所有看板入口（侧边栏、`/boards/<id>`、命令面板）都用 `boardEntrySearch` 明确写入
  协调者自己的 Tab；以前不带 `?tab`，路由会恢复上次选中的子 Tab，比如 reviewer。命令面板的
  数据源仍保留协调者，搜到时显示看板名和看板图标。
- **命名。** 在看板页上，会话侧面板的「文件」改叫「工作区文件」，看板面板里的 tab 叫
  「看板文件」；侧面板框架不变。
- **设置的范围。** 浮窗只编辑现在就生效的字段：名称、目标、规则。项目范围、看板记忆、
  每日摘要在各自的步骤实现前不显示。协调者的模型仍在它的输入框里选。改名时同步改协调者
  会话的标题，让标签和窗口标题一致。

## 第二轮（2026-10-16）

用户用过 `dev-v0.105.0-lan.3` 之后，把看板再往 Claude Projects 靠了一步。
[设计文档](../../../../specs/project-coordinator/design.zh.md)记了决定（第 9–14 条）和实现
（「看板主界面第二轮已实现」）。

- **看板里的对话只在看板里。** 推翻了「线程留在项目组」。`isBoardSession` 在各个外部列表的
  数据源处过滤；关掉实验后线程恢复成普通会话，关实验不会丢东西。
- **不发第一条消息。** 协调者用 `createSession` 创建。用户的第一句话走 `session/create`
  派发路径（这时还没有 ACP 会话），`buildPrompt` 照样追加看板说明。新建时选的运行配置作为
  内存里的运行配置草稿带到输入框；选了 Role 时，输入框本来就会对没有回合的会话读取元数据里
  的 Role 来源。
- **目录都经过本机守护进程。** 桌面拿不到 LAN 凭据，agent 也可能在任何成员上运行，所以都走
  自己机器的守护进程：给消息附件用的 `files` 连接加 `board-list`、`board-put`，读文件复用
  带 `boardId` 的 `range`，桌面预览也就能直接用现有的成员文件资源。宿主机按自己的副本授权，
  提问方副本里过期或伪造的成员资格会在宿主机被拒。
- **记忆用文件，不用 Loro。** agent 本来就擅长读写文件；一题一个记忆文件加一个索引，和
  agent 在别处记记忆的方式一致，用户看到的也就是 agent 写的原文。LoroText 记忆和
  `lody_board_memory_update` 不做了。共享笔记仍是 Loro 文档（并发追加能合并），作为「文件」
  tab 里的一行保留，不用迁移。
- **协调者的定位。** 说明里写明只协调、掌握全局；`lody_board_overview` 加
  `lody_session_history` 已经能读线程进展和结论，所以没有新增工具。
- **线程列表按家族分组。** 以前逐行分组，reviewer 和它的线程状态不同就会被拆开；现在一个
  家族整体移动，归在成员里最强的状态下。

证据：`apps/cli/src/lib/lan/lan-files.test.ts` 在两个真实 TLS 端点之间写入、列出、读取
看板文件，并拒绝非成员（按宿主机副本）和越界路径（含经符号链接越界）。CLI 测试覆盖首条
提示里的指令、目录和协调者说明，以及工具的广告。`board-overview.test.tsx` 覆盖「文件」tab
和经桌面 IPC 的预览、「记忆」页（保存指令、`MEMORY.md` 排在最前）、只填名称且不发首条
消息的新建、切换看板时设置重建、线程家族和外部列表规则。未验证：真实桌面应用、真实多机
LAN、协调者第一句话的完整链路。

## 第二轮复查修正（2026-10-16）

Codex review 后按「防 agent 借看板工具越过自身沙箱或工作区限制、防误操作」的尺度修了六处；
LAN 里所有机器属于同一个用户，同一用户跨机器能碰到文件不算新问题。实现记在
[设计文档](../../../../specs/project-coordinator/design.zh.md)「看板主界面第二轮复查修正」。

- **本机路径复用附件的工作区规则。** 守护进程用自己掌握的会话工作目录（`resolveSessionWorkspaceRoot`，
  chat 会话就是它实际的目录）检查 `source` / `saveTo`，解析链接后再判断；源按真实路径交出去，
  所以经链接指向外面的文件也读不出来。不知道工作目录时直接失败，不退回守护进程的 cwd。
- **目录根从数据目录推出，逐级 lstat。** 原来把 `files/` 的 realpath 当可信根，整个区被换成
  链接时会越界。叶子用 `O_NOFOLLOW` 打开：本机读在 `BoardDirectory.read`，LAN 读只对带
  `boardId` 的 `range` 加这个标志，会话文件和预览路径的打开方式不变。检查后父目录被替换的
  竞态按已知限制记在 Spec，没有上目录句柄。
- **协调者永不走空会话删除。** 判断抽成 `closeSessionTab`（`session-tab-close-target.ts`），
  页面的关闭回调和测试走同一个函数。
- **`boardThread` 交给面板。** 面板的 `openMember` 同时服务线程行和 URL 请求，面板手里有完整
  的会话元数据，比页面按子会话列表猜更准。页面先清 URL 再交请求：反过来的话，窄屏上面板先
  导航到线程页，页面清参数时又会把它拉回协调者页面。命令面板的搜索参数抽成
  `boardMemberEntrySearch`，测试从它走到面板。
- **二进制下载复用 `saveMemberFile`。** Electron 端的成员文件 schema 早已接受 `boardId`，
  不用改。
- **设置导航的焦点改成轮廓，只在看板浮窗里改。** 全局设置窗口共用的 `settingsSurface.listRow`
  也是悬停 6%、焦点 6%、选中 10% 的浅底，键盘导航时同样会像两行同时选中；没动它，留给全局
  设置自己决定。

**混版客户端：不做兼容，要求统一升级。** 旧客户端的 `normalizeBoardMeta` 用 zod 对象解析，
会去掉 `instructions`、`files`，并拒绝目标为空的看板；它只要写一次看板行（保存设置含改名、
归档、恢复）就把两个字段丢掉。为此加兼容层要在旧版本里改，做不到；看板还在实验开关后面，
所以按「能写看板的客户端统一升级」处理，后果写在 Spec 里。

证据：`apps/cli/src/mcp/board-tools.test.ts` 用真实 `BoardDirectory` 和 `LanFileHandoff`、
真实文件系统，覆盖工作目录内正常读写、越界源（直接、叶子链接、目录链接）和越界目的地（直接、
目录链接）。`lan-files.test.ts` 加了区域根和看板目录本身是链接时的拒绝、叶子是链接时本机和
跨成员读的拒绝。`board-overview.test.tsx`：真实对话框建出的协调者经 `closeSessionTab` 关闭后
仍在、看板行不变，普通空 Tab 仍被删除（去掉判断后该测试失败）；命令面板参数经面板请求打开
协调者 Tab / Side Chat / 独立线程，各只有一个 surface；「文件」tab 里二进制文件经
`saveMemberFile` 下载。截图：Storybook + Playwright，1440px 和 390px，下载入口与设置导航
的打开、键盘焦点、悬停三态。未验证：真实桌面上的保存对话框、紧凑桌面上 `boardThread` 的
面板交接（代码路径和手机相同，面板需已挂载）。

## lan.4 实测修正（2026-10-17）

用户在 `dev-v0.105.0-lan.4`（五台机器的守护进程都是这一版）上实际用下来，只有设置浮窗正常。
实现记在[设计文档](../../../../specs/project-coordinator/design.zh.md)「看板 lan.4 实测修正」。

- **`BOARD_NOT_FOUND` 是成员机器的 catalog 副本没同步。** 现场证据：在每台机器上直接向本机
  守护进程的 control socket 发桌面用的 `board/files-list`（看板 `bd_ce75…`，协调者在 devNuc）。
  devNuc（宿主）和 homeN100 返回空列表；mba 返回
  `BOARD_NOT_FOUND:this machine knows no such Board`，这条报错来自发起方自己读看板行的 `LanFileHandoff.boardOf`，请求根本没发到宿主机。
  在 mba 上跑一次会让守护进程同步 workspace catalog 的 `lody-lan mcp list` 之后，同一请求立即
  返回列表。代码上，读 catalog 的其他地方（看板工具、成员启动提示、Role / MCP 读取）都先
  `syncFlockDocOrThrow`，只有 `lody-fleet.ts` 的 `readBoard` 直接读本地副本。修法是抽出
  `readSyncedBoard`（`board-directory.ts`），先同步、失败告警后沿用本地行。
- **50/50 没生效是旧宽度带进看板。** mba 桌面 localStorage 里的 `board-detail-panels` 存着
  `[61.8, 38.2]` 和 `[100, 0]`。`DesktopSessionDetailLayout` 的 `lastSidebarSizeRef` 在布局键
  换掉后仍是普通会话的侧栏宽度，侧栏打开时按它 `resize`，`autoSaveId` 再把它存进看板的键。
  现在看板页不记忆分栏（`layoutStorageId={null}`），侧栏重开宽度按布局区分，用户机器上已存的
  旧值也就不再读取。
- **看板文件 tab 换成会话文件树。** `BoardDirectoryFileProvider` 建在 `LazyDirectoryFileProvider`
  上，根目录一次给出全部文件，树按路径建目录；`openFile` 明确返回不可用，因为点开文件由看板
  预览负责（它还管下载）。没有接会话的查看器 tab：那套按会话路径解析文件，换数据源要动查看器。
  共享笔记留在树上方，不改成 `notes.md`，省掉迁移且不丢合并语义。设置里的「记忆」页仍是平铺列表
  （`MEMORY.md` 排第一）。

证据：`lan-files.test.ts` 新用例里，成员的 catalog 是一个真实 `LoroRepo`，只有同步时才拿到看板
行；同步失败时报 `BOARD_NOT_FOUND`，同步后经两个真实 TLS 端点列出、写入、读取都成功。
`desktop-session-detail-layout.test.tsx` 覆盖「普通会话拖到 38% 后进看板，侧栏按 50 打开且不存
分栏」（未修时 `resize(38.2)`）。`board-overview.test.tsx` 的「文件」tab 用例改走文件树：展开
目录、点开预览、返回后目录仍展开、二进制下载。截图 `/tmp/board-lan4fix-files-*.png`。
未验证：修复版本还没部署，真实 LAN 上的修复后读写要等下一个 dev 包；mba 的副本已经因为调查时那次
同步变新，修复前状态只能在其他没同步过的成员上再现；Windows 上的复现因 shell 转义没做成。

## 看板入口的操作（2026-10-17）

用户反馈看板上「没有任何可以操作的地方」，希望看板的右上和对话的右上一致，至少能归档、分享。
决定记在[设计文档](../../../../specs/project-coordinator/design.zh.md)「已决定」第 15 条，逐项
处理见「看板入口的操作」。

- **调研结果。** 桌面看板页的头部其实已经是对话头部（`SessionChatInterface` 的 toolbar），
  「…」菜单和分享控件都在，但重命名、归档只作用于协调者会话：归档后看板行还在、成员还开着，
  侧边栏留下一个打不开的看板。分享控件在 1440 宽、50/50 分栏下因容器不到 800px 而收进「…」
  菜单（和普通会话一样）。侧边栏看板行是一个普通按钮，没有任何菜单。Storybook 的看板 story
  头部只画了设置按钮，所以截图里也看不到这些操作。
